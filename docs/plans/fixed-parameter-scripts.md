# 固定脚本与参数统一方案

状态：待实现。记录日期：2026-10-24。本次仅记录后续工作，不修改现有实现。

## 目标与范围

后续将页面提供的终端脚本统一为「固定脚本 + 参数」形式，替代服务端根据模板填变量生成脚本的方式。覆盖单个镜像下载、批量镜像下载，并梳理安装、离线包下载及卸载相关脚本；各领域保留独立脚本，不合并成一个通用脚本。

用户接受较长的复制命令，只要能正确执行；缩短命令、提供清单文件或脚本文件下载不是本次待办的必要目标。当前批量脚本及其他页面的模板生成方式暂时保留。

## 实现入口与对接

- 镜像：从 `src/client/features/download/compose.js`、同目录 `index.js` 与 `public/download-images.sh` 接入；梳理 `src/api/routes/download/terminal.ts` 和 `image-archive-script.ts` 的模板逻辑，将客户端运行逻辑迁移为固定脚本。单个传一组参数，批量传多组参数，复用同一镜像下载能力，最终消除批量脚本再次获取单镜像脚本的嵌套方式。
- 安装：从 `src/client/features/install/index.js` 与 `src/api/routes/install/` 梳理模板、下载、安装和卸载调用链；明确各脚本职责及运行参数，再按领域迁移。固定脚本作为源码资产维护，沿用 `public/` 的构建复制机制。
- 服务端继续负责必要的元数据解析、下载计划及 Registry 流式透传；不将大文件缓冲到服务端，也不另建浏览器任务或缓存生命周期。业务依赖保持在所属模块及公共层边界内。

## 参数、兼容与风险

- 参数需覆盖镜像引用（标签或 digest）、完整平台变体、镜像源、站点地址，以及安装领域实际需要的版本和配置；具体契约在实施前结合现有代码确定。
- 固定脚本不写死部署域名；页面生成复制命令时带入当前站点地址作为参数。脚本通过静态资源服务分发，必要的动态信息通过现有或兼容的数据接口获取，不能只将模板生成请求藏进固定脚本而视为迁移完成。
- 参数始终作为数据处理，校验数量、缺失值与格式，正确处理 shell 转义和 URL 编码；禁止使用 eval 拼接执行用户参数。
- 先明确 shell、curl、tar 和 JSON 解析的依赖与最低版本；是否引入 jq 待实现时评估，不在本计划中预先确定。
- 保留逐镜像 TAR、校验、已有文件保护、失败退出与临时文件清理；安装与卸载保留权限检查、配置保护、回滚及幂等行为。
- 页面切换与历史脚本接口兼容分阶段处理，不能直接移除现有接口；评估固定脚本更新与旧页面参数契约的兼容，避免缓存版本错配。

## 实施顺序与验收

1. 盘点脚本入口、参数和依赖，确定各领域固定脚本契约及兼容策略。
2. 先统一单个与批量镜像下载，再迁移安装相关脚本；每一步同步页面命令、相关测试及所属现行文档。
3. 使用真实 shell 加模拟传输验证参数传递、特殊字符、失败中断、信号清理和临时文件清理；覆盖单个、多项、digest、平台变体、镜像源及重复目标。
4. 安装领域验证缺失依赖、权限、已有配置、失败回滚、重复安装与卸载；确保行为不因脚本形式变化而改变。
5. 执行 `pnpm run validate`，检查构建中脚本可访问、页面命令可执行，并记录实际远端与环境验证范围；完成后更新现行文档并归档计划。
